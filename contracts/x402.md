# x402 SDK cases

The [x402 corpus](../fixtures/x402.mjs) checks InFlow Core, Buyer, and Seller behavior through
public SDK entry points. Generate its case index for the [runner](../runner/README.md):

```sh
node fixtures/x402.mjs > /tmp/inflow-x402-cases.json
```

Select `x402-core`, `x402-buyer`, and/or `x402-seller`. Cases in a selected suite are mandatory.
These are development fixtures, not runtime validation or a facilitator implementation.

## Sources and limits

The wire contract follows the
[x402 V2 specification](https://github.com/x402-foundation/x402/blob/dc656bb8bcc2a9ba7ef2f054f255175b63e59322/specs/x402-specification-v2.md),
[HTTP transport](https://github.com/x402-foundation/x402/blob/dc656bb8bcc2a9ba7ef2f054f255175b63e59322/specs/transports-v2/http.md),
and
[payment identifier extension](https://github.com/x402-foundation/x402/blob/dc656bb8bcc2a9ba7ef2f054f255175b63e59322/specs/extensions/payment_identifier.md).
InFlow-specific request shapes and response statuses were checked against the platform
implementation. Private platform source is not distributed here.

The Node reference is commit
[`bfa2c3f`](https://github.com/inflowpayai/inflow-node/tree/bfa2c3f88b6f0c104f39887dce15779b88d42885):

- [Payment identifier support](https://github.com/inflowpayai/inflow-node/blob/bfa2c3f88b6f0c104f39887dce15779b88d42885/packages/x402/src/extensions/payment-identifier.ts).
- [Buyer client](https://github.com/inflowpayai/inflow-node/blob/bfa2c3f88b6f0c104f39887dce15779b88d42885/packages/x402-buyer/src/inflow-client.ts)
  and
  [signing lifecycle](https://github.com/inflowpayai/inflow-node/blob/bfa2c3f88b6f0c104f39887dce15779b88d42885/packages/x402-buyer/src/signer.ts).
- [Facilitator client](https://github.com/inflowpayai/inflow-node/blob/bfa2c3f88b6f0c104f39887dce15779b88d42885/packages/x402-seller/src/facilitator.ts),
  [offer construction](https://github.com/inflowpayai/inflow-node/blob/bfa2c3f88b6f0c104f39887dce15779b88d42885/packages/x402-seller/src/inflow-accepts.ts),
  and
  [sponsorship advertisement](https://github.com/inflowpayai/inflow-node/blob/bfa2c3f88b6f0c104f39887dce15779b88d42885/packages/x402-seller/src/inflow-route.ts).

All accounts, keys, payment identifiers, and signatures are synthetic. The mock does not verify
signatures, debit balances, or broadcast transactions. A successful mocked response proves SDK
handling of that response, not that the platform would accept the supplied payment. Configurations
exercise advertised capabilities; they do not assert that a particular deployment advertises them.

Passing these cases does not certify foundation middleware, external-wallet signing, sponsorship
execution, live metered settlement, optional MCP, TAP, or server replay protection. Those require
their own integration and end-to-end checks. No adapter may implement missing SDK behavior to make a
case pass.

## Operations

`base_url` is injected by the runner only for mock HTTP cases. SDK clients must use it through their
public configuration. They must not contact the resource's illustrative `seller.example` address or
a production InFlow host.

| Operation                          | Input                                                                       | Observation                                                                    |
| ---------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `x402.core.identifier-valid`       | `value`                                                                     | Boolean validity result                                                        |
| `x402.core.identifier-declaration` | Empty object                                                                | Complete extension declaration                                                 |
| `x402.core.identifier-entry`       | `declaration`, `payment_id`                                                 | Complete extension entry or null                                               |
| `x402.buyer.sign`                  | `api_key`, `requirement`, `context`, `payment_id`; optional timing settings | `encodedPayload`, `paymentPayload`, `transactionId`, or failure                |
| `x402.buyer.cancel`                | Same buyer input                                                            | Cancellation failure after cancelling the prepared payment                     |
| `x402.buyer.concurrent-await`      | Same buyer input                                                            | Shared payment result from two concurrent waits                                |
| `x402.seller.verify`               | `payment_payload`, `payment_requirements`; optional `api_key`               | Complete verification response                                                 |
| `x402.seller.settle`               | Same facilitator input                                                      | Complete settlement response or HTTP failure                                   |
| `x402.seller.verify-settle`        | Same facilitator input                                                      | `{verification, settlement}` on valid verification; `{verification}` otherwise |
| `x402.seller.offers`               | `config`, `options`                                                         | Ordered payment options                                                        |
| `x402.seller.route`                | `config`, `supported`, `options`                                            | Route with offers and applicable extension declarations                        |

### Buyer lifecycle

Use the SDK's public two-phase payment API: prepare the payment, then await its signed payload. Do
not implement create/poll requests in the adapter. Configure `poll_interval_ms` and `timeout_ms`
through the SDK; defaults for these tests are 1 ms and 2000 ms. These are test settings, not
recommended production polling intervals.

Cancellation calls the prepared handle's cancel operation after preparation, then observes the
result of awaiting that handle. It does not certify interruption of an in-flight network request.
Concurrent-await starts two waits on one prepared handle and requires both complete results to
match, while the mock requires only one polling request. Return that common result.

The adapter must not add cancellation to a two-phase failure case: ownership of that handle remains
with its caller. A one-shot API with automatic cancellation is a different lifecycle.

Signing is not settlement. A nonterminal status without a payload continues waiting; a signed
payload must retain its encoded representation and decoded data. Permit2 cannot use InFlow-managed
signing even when an exact network is advertised. Unsupported combinations must not create an
approval. Creation failures must not transparently create a second payment.

Each wait attempt has its own deadline, covering poll requests and delays between polls. A late
payload must not turn an expired wait into success. Transaction creation has a separate request
timeout. Polling retries network failures, HTTP 429 and HTTP 5xx within the wait budget; other HTTP
failures preserve their status and body immediately. Credential-provider failures propagate without
polling retries. None of these failures recreates the payment or automatically cancels a two-phase
handle owned by the caller.

The delayed-poll case checks the timeout result and request sequence, not timely interruption of the
connection. Native SDK tests must also interrupt an active HTTP response at the deadline and verify
cleanup of timers and cancellation listeners.

Seller probe and payment-replay helpers return redirects without following them. Native tests must
use separate local origins and verify that payment signatures, credentials and request bodies are
not forwarded. These helper checks do not certify a caller's independent HTTP transport. Private-key
decoding errors must not contain supplied key material, including parser excerpts.

### Seller operations

Use the SDK's public facilitator client. Omit credentials for anonymous facilitator cases. A valid
payment identifier is preserved; absent identifiers are derived by the SDK, not inserted by the
adapter. The reference derivation for transaction IDs, serialized transactions, and signatures is
`pay_` plus the first 32 lowercase hexadecimal characters of SHA-256 over `key:value`. This is an
InFlow SDK convention, not a requirement of x402 itself. Unknown extensions and caller-owned objects
must remain intact.

Verification and settlement are separate public operations. `verify-settle` is explicitly a
composition check: call verify, and call settle only when its returned `isValid` is true. It does
not prove that a framework protects a handler in the same sequence. All retry behavior belongs to
the SDK, not this composition.

HTTP 200 with `isValid: false` or `success: false` is returned as that complete response, never
converted into successful payment. A recognized allowance-required HTTP 412 body is a verification
result. An unrelated 412 remains an HTTP failure. Settlement retries are limited to HTTP 409 with
`errorReason: idempotency_pending`; the complete request, including its identifier, remains
unchanged. The reference budget is five total attempts. Test responses use `Retry-After: 0` to avoid
slow tests; they do not change the platform's production `Retry-After: 5` or certify delay
calculations.

Offer and route cases supply configuration through the SDK's public configuration-provider
interface. That provider may return `config` and `supported` unchanged; it must not construct offers
or decide sponsorship itself. These cases do not test configuration fetching or caching. Amounts
must remain exact decimal strings, including values larger than a JavaScript safe integer. A price
that requires truncating nonzero digits is rejected. Scheme and network filters intersect. Metered
offers require explicit selection and complete advertised Permit2 metadata. Sponsorship requires
both asset and facilitator support; absence is not permission to assume support.

## Failure observations

These classifications are for the test adapter only, not SDK exception names or user-facing text.
Map recognized typed errors or structured failures. Unknown exceptions must fail the adapter; never
classify from the case name or its expected result.

| Code                     | Message                           | Additional observation                               |
| ------------------------ | --------------------------------- | ---------------------------------------------------- |
| `invalid-input`          | `Invalid input.`                  | None                                                 |
| `payment-failed`         | `Payment failed.`                 | `details.status` preserves the transaction status    |
| `payment-timeout`        | `Payment timed out.`              | None                                                 |
| `payment-cancelled`      | `Payment cancelled.`              | Required cancellation exchange is checked separately |
| `unsupported-capability` | `Unsupported payment capability.` | No payment creation request                          |
| `api-error`              | `InFlow API request failed.`      | `http_status` and complete `details.body`            |

Synthetic HTTP failures deliberately include bodies not shaped like a normal InFlow error. The
complete body and status remain observable; this contract does not invent a platform error code for
them. The shared runtime cases separately test normal InFlow error envelopes.

## Verification

`pnpm verify` validates fixture structure, cross-field relationships, and the mock exchanges. Those
tests are not SDK conformance. A maintained adapter must execute the public SDK APIs against these
mocks and emit the actual observations through the runner. Check caller-owned inputs after both
successful and rejected operations. Do not derive an observation from the scripted response.
